# ADR-017: Estratégia de Testes e Qualidade (QA)

- **Status:** Proposto
- **Data:** 2026-09-14
- **Decisores:** [Seu Nome / Equipe]
- **Contexto Técnico:** Definição da pirâmide de testes, ferramentas e critérios de qualidade para o MVP
- **Tags:** `testes`, `qa`, `qualidade`, `ci`, `regras`, `transversal`
- **Depende de:** ADR-006 (Motor de Resolução de Ações), ADR-014 (Escopo do MVP), ADR-018 (DevOps e CI/CD)
- **Tipo:** ADR Transversal

---

## 1. Contexto

Nenhum dos ADR-001 a ADR-014 define como a correção das regras será verificada, nem que tipo de teste é exigido antes de um merge. Isso é particularmente arriscado para o **Motor de Resolução de Ações** (ADR-006): é o núcleo mecânico do produto, e um erro sutil (ex.: falha crítica contada errado, sucesso automático não sendo blindado contra cancelamento) mina a confiança do usuário no sistema todo. A revisão arquitetural do conjunto de ADRs também identificou como risco não endereçado a **concorrência na edição de fichas em tempo real** (ADR-004) — sem uma estratégia de testes que cubra isso, bugs de sincronização só apareceriam em produção, com jogadores reais em sessão.

Este ADR define a estratégia de testes para o MVP (ADR-014), com foco em onde o risco de regressão é mais caro: motor de dados, sistemas dramáticos e sincronização em tempo real.

---

## 2. Decisão

### 2.1. Pirâmide de Testes

| Camada | Ferramenta | Cobertura Alvo (MVP) | O que testa |
|--------|-----------|------------------------|--------------|
| **Unitária** | Vitest/Jest (backend NestJS e frontend React) | ≥ 85% no Motor de Resolução (ADR-006) e Motor de Disciplinas (ADR-005); ≥ 70% no restante do backend | Funções puras: cálculo de sucessos, dificuldade, custo de experiência, efeitos de Disciplina isolados. |
| **Integração** | Vitest/Jest + banco de teste (Testcontainers com Postgres real) | Todos os fluxos de API principais (criação de personagem, rolagem, combate) | Interação entre serviços reais e banco de dados, sem mocks de persistência. |
| **Contrato/WebSocket** | Testes dedicados com cliente WS real contra o backend | Sincronização de ficha, rolagens em tempo real | Que eventos emitidos batem com o schema esperado pelo frontend. |
| **E2E** | Playwright | Os fluxos da "Definição de Pronto do MVP" (ADR-014, §2.3) | Fluxo completo no navegador: criar conta → criar personagem → jogar uma cena → ver resultado. |
| **Regras Golden Master** | Testes de propriedade + casos fixos do livro | Motor de Resolução e tabelas (Vitalidade, Pontos de Sangue por Geração) | Compara contra exemplos do livro (ADR-006 §5, "Exemplos de Testes", p. 254-255) e contra as tabelas já auditadas na verificação de fidelidade dos ADRs. |

### 2.2. Testes do Motor de Resolução (Prioridade Máxima)

**Decisão:** O Motor de Resolução de Ações (ADR-006) exige uma suíte de testes própria, incluindo **testes estatísticos** além dos testes determinísticos.

```
Casos obrigatórios:
├── Sucesso simples (N dados, dificuldade D) → contagem de sucessos correta
├── Falha crítica: 0 sucessos líquidos com pelo menos um "1"
├── Cancelamento: sucessos e "1"s se cancelando corretamente (não pode dar líquido negativo tratado como sucesso)
├── Sucesso automático (gasto de Força de Vontade) NUNCA é cancelado por falha crítica
├── Especialidade: "10" conta como 2 sucessos apenas quando aplicável
├── Ações resistidas: vencedor = maior diferença de sucessos líquidos; empate tratado corretamente
└── RNG: distribuição estatística dos resultados (teste de qui-quadrado em amostra grande) para garantir que crypto.randomInt não introduz viés perceptível
```

**Regra de qualidade:** nenhuma mudança no Motor de Resolução é mesclada sem que a suíte acima passe — este é o único módulo com **cobertura obrigatória de 100% de branches**, dado seu papel central.

### 2.3. Testes de Concorrência (Ficha em Tempo Real)

**Decisão:** Testar explicitamente o cenário de **edição concorrente** identificado como risco na revisão arquitetural: dois clientes (Narrador e Jogador) alterando a mesma ficha quase simultaneamente via WebSocket.

- Teste de integração que dispara duas mutações concorrentes na mesma ficha e verifica que o resultado final é consistente (sem perda de escrita silenciosa) e que todos os clientes conectados convergem para o mesmo estado.
- A estratégia de resolução de conflito em si — **controle de concorrência otimista (OCC) por seção da ficha** — está definida no ADR-004, seção 2.13. Este ADR (2.3) exige que essa estratégia tenha testes de concorrência (escrita simultânea rejeitada corretamente, todos os clientes convergindo para o mesmo estado) antes de ir a produção.

### 2.4. Dados de Teste e Fixtures

**Decisão:** Manter um conjunto de **fixtures canônicas** derivadas do livro, reaproveitando a verificação de fidelidade já feita sobre os ADR-003/004/005/008 (Clãs, Disciplinas, tabela de Geração, Trilhas).

```
fixtures/
├── personagens-exemplo/       # Personagens pré-gerados (um por Clã do MVP, ADR-014 §2.2)
├── tabelas-canonicas.json     # Pontos de Sangue por Geração, Vitalidade, Dificuldades padrão
└── exemplos-livro/            # Casos de teste tirados literalmente dos exemplos do livro (p. 254-255 etc.)
```

Qualquer alteração numa fixture canônica exige justificativa explícita no PR (ex.: "o livro define X, mas decidimos uma regra da casa Y") — evita que uma correção de bug silenciosamente reintroduza uma divergência de regra já detectada e corrigida (como a de páginas do ADR-003).

### 2.5. Gate de CI e Processo de Release

**Decisão:** Nenhum merge para a branch principal sem: lint, type-check, testes unitários e de integração passando. Testes E2E rodam no pipeline de deploy para staging (ver ADR-018), não em todo PR, para manter o ciclo de PR rápido.

| Gate | Quando roda | Bloqueia merge? |
|------|--------------|-------------------|
| Lint + type-check | Todo PR | Sim |
| Testes unitários | Todo PR | Sim |
| Testes de integração | Todo PR | Sim |
| Testes de contrato/WebSocket | Todo PR que toca backend realtime | Sim |
| E2E (Playwright) | Deploy para staging | Sim (bloqueia promoção a produção) |
| Testes estatísticos do RNG | Nightly (agendado) | Não bloqueia PR, mas gera alerta |

### 2.6. Playtesting Manual

**Decisão:** Complementar aos testes automatizados, exigir **pelo menos uma sessão de playtesting manual completa** (seguindo a Definição de Pronto do MVP, ADR-014 §2.3) antes de cada release para produção, conduzida por alguém que não escreveu o código da funcionalidade testada.

## 3. Consequências

### 3.1. Positivas
- Cobertura obrigatória de 100% de branches no Motor de Resolução reduz drasticamente o risco de um bug de regra minar a confiança no produto.
- Fixtures canônicas ligadas à verificação de fidelidade já realizada evitam regressão silenciosa de regras corrigidas.
- Testes de concorrência tornam explícito um risco que hoje está apenas documentado, forçando uma decisão de design antes da implementação da sincronização.

### 3.2. Negativas
- Exigir Testcontainers com Postgres real para testes de integração aumenta o tempo de CI comparado a mocks — mitigado por rodar em paralelo.
- Testes estatísticos de RNG são mais lentos e não determinísticos por natureza — rodam fora do gate de PR (nightly) para não travar o fluxo de desenvolvimento.
- Playtesting manual obrigatório adiciona uma dependência humana ao processo de release, que precisa ser agendada com antecedência.

### 3.3. Alternativas Descartadas

| Alternativa | Motivo da Rejeição |
|-------------|---------------------|
| **Cobertura uniforme de 80% em todo o código** | Trataria o Motor de Resolução com o mesmo rigor que uma tela de configurações; não reflete o risco real desigual entre módulos. |
| **Mocks de banco de dados em todos os testes de integração** | Esconderia bugs reais de query/schema que só aparecem contra um Postgres real. |
| **E2E em todo PR** | Tornaria o ciclo de PR lento demais; E2E roda no pipeline de staging em vez disso. |
| **Sem testes estatísticos de RNG** | Um RNG enviesado (mesmo que sutil) mina diretamente a percepção de justiça do jogo; vale o custo de testes nightly dedicados. |

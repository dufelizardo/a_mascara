# ADR-006: Motor de Resolução de Ações (Core Dice Engine)

- **Status:** Proposto
- **Data:** 2026-09-14
- **Decisores:** [Seu Nome / Equipe]
- **Contexto Técnico:** Implementação do sistema central de resolução de ações (paradas de dados)
- **Tags:** `regras`, `dados`, `sistema`, `storyteller`, `resolução`, `vampiro-a-mascara`
- **Depende de:** ADR-001 (Plataforma e Arquitetura Geral), ADR-004 (Ficha de Personagem), ADR-005 (Motor de Disciplinas)

---

## 1. Contexto

O **Capítulo Cinco: Regras** define o **sistema Storyteller** — o núcleo mecânico de *Vampiro: A Máscara*. É o motor que resolve todas as ações incertas no jogo, desde um simples teste de Percepção até um combate brutal ou um ritual de Taumaturgia. É o "coração" mecânico do jogo, e sua implementação precisa ser precisa, rápida e transparente.

O sistema é baseado em:
- **Paradas de Dados (Dice Pools):** A soma de um Atributo + uma Habilidade (ou outra combinação).
- **Dados de 10 lados (d10):** Rolados para determinar sucesso ou falha.
- **Dificuldade:** Um número de 2 a 10 que o dado precisa igualar ou superar para ser um sucesso.
- **Sucessos:** Cada dado que rola igual ou acima da dificuldade.
- **Falhas Críticas:** Dados que rolam "1" cancelam sucessos.
- **Tipos de Ações:** Simples, Estendida, Resistida, Reflexiva.
- **Sucessos Automáticos:** Gasto de Força de Vontade para obter um sucesso garantido.
- **Modificadores:** Ajustes de dificuldade baseados em circunstâncias.

A plataforma precisa implementar esse motor de forma que:
- Seja **preciso** — as regras do livro sejam seguidas fielmente.
- Seja **rápido** — as rolagens aconteçam quase instantaneamente.
- Seja **transparente** — os jogadores vejam os resultados e entendam o que aconteceu.
- Seja **justo** — a aleatoriedade seja verdadeira (não tendenciosa).
- Seja **flexível** — o Narrador possa modificar dificuldades, aplicar bônus/penalidades e ignorar regras.
- Seja **auditável** — todas as rolagens sejam registradas em log.

Este ADR define **como implementar o Motor de Resolução de Ações** na plataforma, estabelecendo as bases para os Sistemas Dramáticos (ADR-007) e a Moralidade (ADR-008).

---

## 2. Decisão

Decidimos implementar o Motor de Resolução de Ações através de **oito pilares fundamentais**, cada um representando um aspecto do Capítulo Cinco.

### 2.1. Estrutura Geral do Motor de Resolução

**Decisão:** O motor é implementado como um **módulo dedicado no backend**, com uma API bem definida, que recebe uma **requisição de ação** e retorna um **resultado de ação**.

**Estrutura de Dados:**

```
RequisiçãoDeAção (ActionRequest)
├── id: UUID
├── personagem: UUID                    # Quem está agindo
├── tipo: enum                          # Simples | Estendida | Resistida | Reflexiva
├── atributo: string                    # Ex: "Força", "Manipulação", "Percepção"
├── habilidade: string                  # Ex: "Briga", "Lábia", "Ocultismo"
├── modificadores: [Modificador]        # Bônus/penalidades
├── dificuldade: int                    # 2-10 (opcional, o Narrador pode definir)
├── especialidade: string               # Especialidade aplicável (opcional)
├── forca_vontade: int                  # Pontos de Força de Vontade a gastar
├── alvo: UUID                          # Alvo (para ações resistidas)
├── contexto: Contexto                  # Contexto da ação (ex: "combate", "social")
└── notas: text                         # Notas do jogador

ResultadoDeAção (ActionResult)
├── id: UUID
├── requisicao: UUID                    # Referência à requisição
├── dados_rolados: [int]                # Resultados individuais dos dados
├── dificuldade_final: int              # Dificuldade após modificadores
├── sucessos: int                       # Número de sucessos
├── falhas_criticas: int                # Número de "1"s
├── sucessos_liquidos: int              # Sucessos - falhas críticas
├── resultado: enum                     # Sucesso | Falha | Falha Crítica
├── descrição: text                     # Descrição narrativa do resultado
├── efeitos: [Efeito]                   # Efeitos aplicados (dano, condições, etc.)
├── data: datetime                      # Quando ocorreu
└── visibilidade: enum                  # Público | Privado | Secreto
```

### 2.2. Paradas de Dados (Dice Pools)

**Decisão:** A parada de dados é calculada somando um **Atributo + Habilidade** (ou outra combinação definida pelo Narrador).

**Regras:**

- **Cálculo Padrão:** `Parada de Dados = Atributo + Habilidade`.
- **Limite de Dados:** O número máximo de dados em uma parada é 10 (para mortais); vampiros anciões podem ter mais.
- **Modificadores:** Bônus/penalidades são aplicados **antes** da rolagem (ex: +2 dados, -1 dado).
- **Especialidades:** Se o personagem tem uma Especialidade aplicável, cada "10" conta como **2 sucessos** em vez de 1.
- **Habilidades sem Nível:** Se o personagem não tem a Habilidade, usa o Atributo base com dificuldade +1 (para Perícias) ou sem penalidade (para Talentos).

**Estrutura de Dados:**

```
ParadaDeDados (DicePool)
├── atributo: int                       # Valor do Atributo
├── habilidade: int                     # Valor da Habilidade
├── modificadores: int                  # Soma dos modificadores
├── total: int                          # Total de dados
├── especialidade: bool                 # Se aplica Especialidade
└── notas: text                         # Notas sobre a composição
```

**Exemplo:**

```
Personagem: Brujah com Força 4 e Briga 3
Parada de Dados: 4 + 3 = 7 dados
Modificador: +2 (usando Potência)
Total: 9 dados
Especialidade: "Punhos de Ferro" (aplicável)
```

### 2.3. Dificuldade e Sucessos

**Decisão:** A dificuldade é um número de 2 a 10, definido pelo Narrador (ou pelo sistema, com base na tabela padrão). Cada dado que rola igual ou acima da dificuldade é um **sucesso**.

**Tabela de Dificuldades Padrão:**

| Dificuldade | Descrição | Exemplos |
|-------------|-----------|----------|
| 3 | Trivial | Rastrear um rosto familiar em uma pequena multidão |
| 4 | Fácil | Seguir um rastro de sangue |
| 5 | Simples | Seduzir alguém que já está "no clima" |
| 6 | Normal | Disparar uma arma |
| 7 | Desafiador | Localizar de onde provêm sussurros agonizantes |
| 8 | Difícil | Convencer um policial de que a cocaína não é sua |
| 9 | Extremamente Difícil | Andar em uma corda bamba |
| 10 | Quase Impossível | Realizar uma façanha sobre-humana |

**Graus de Sucesso:**

| Sucessos | Grau | Descrição |
|----------|------|-----------|
| 1 | Mínimo | Sucesso por um fio |
| 2 | Moderado | Sucesso razoável |
| 3 | Total | Sucesso completo |
| 4 | Excepcional | Sucesso acima do esperado |
| 5+ | Fenomenal | Sucesso lendário |

**Estrutura de Dados:**

```
ResultadoDeDados (DiceResult)
├── dados: [int]                        # Resultados individuais
├── dificuldade: int                    # Dificuldade alvo
├── sucessos: int                       # Dados >= dificuldade
├── falhas_criticas: int                # Dados == 1
├── sucessos_liquidos: int              # sucessos - falhas_criticas
├── grau: enum                          # Mínimo | Moderado | Total | Excepcional | Fenomenal
└── resultado: enum                     # Sucesso | Falha | Falha Crítica
```

### 2.4. Falhas Críticas

**Decisão:** Um dado que rola "1" é uma **falha crítica**, que cancela um sucesso.

**Regras:**

- Cada "1" cancela **um** sucesso.
- Se, após o cancelamento, **não sobrar nenhum sucesso** e houver pelo menos um "1", é uma **Falha Crítica**.
- Uma Falha Crítica é **pior** que uma falha simples: algo desastroso acontece.
- O Narrador decide o que dá errado (ex: arma emperra, aliado é atingido, informação falsa é obtida).

**Exemplo:**

```
Rolagem: 3, 8, 7, 10, 1, 1
Dificuldade: 6
Sucessos: 8, 7, 10 = 3 sucessos
Falhas Críticas: 1, 1 = 2 falhas
Sucessos Líquidos: 3 - 2 = 1 sucesso
Resultado: Sucesso Mínimo
```

```
Rolagem: 3, 4, 1, 1, 2, 5
Dificuldade: 6
Sucessos: 0
Falhas Críticas: 2
Sucessos Líquidos: 0 - 2 = -2
Resultado: Falha Crítica
```

**Funcionalidades:**

- O sistema calcula automaticamente as falhas críticas.
- O Narrador é notificado quando ocorre uma Falha Crítica.
- O Narrador pode escolher o efeito da Falha Crítica (de uma lista de sugestões).
- O sistema registra a Falha Crítica no log.

### 2.5. Tipos de Ações

**Decisão:** O motor suporta **quatro tipos de ações**, cada uma com regras específicas.

#### 2.5.1. Ações Simples

**Definição:** Uma ação que requer **apenas um sucesso** para ser bem-sucedida.

**Regras:**

- O jogador rola a parada de dados uma vez.
- Se obtiver pelo menos 1 sucesso líquido, a ação é bem-sucedida.
- Sucessos extras podem melhorar o resultado (a critério do Narrador).

**Exemplo:** Desviar de uma bala, pressentir uma emboscada, disparar uma arma.

#### 2.5.2. Ações Estendidas

**Definição:** Uma ação que requer **múltiplos sucessos** ao longo de vários turnos.

**Regras:**

- O Narrador define o número total de sucessos necessários.
- O jogador rola a parada de dados a cada turno.
- Os sucessos são acumulados.
- Uma Falha Crítica pode reiniciar a contagem (a critério do Narrador).
- O intervalo entre os testes pode ser de um turno, uma hora, uma noite, etc.

**Exemplo:** Escalar uma montanha, pesquisar um ritual, hackear um sistema.

**Estrutura de Dados:**

```
AçãoEstendida (ExtendedAction)
├── id: UUID
├── personagem: UUID
├── atributo: string
├── habilidade: string
├── dificuldade: int
├── sucessos_necessarios: int           # Total de sucessos para completar
├── sucessos_acumulados: int            # Sucessos obtidos até agora
├── intervalo: string                   # Ex: "1 turno", "1 hora", "1 noite"
├── tentativas: int                     # Número de tentativas feitas
├── status: enum                        # Em Andamento | Concluída | Falhada
└── log: [ResultadoDeAção]              # Histórico de rolagens
```

#### 2.5.3. Ações Resistidas

**Definição:** Uma ação em que **dois personagens competem** diretamente.

**Regras:**

- Ambos os personagens rolam suas paradas de dados.
- A dificuldade de cada um é geralmente determinada por uma Característica do oponente.
- Compara-se o número de sucessos.
- O personagem com **mais sucessos** vence.
- Os sucessos do perdedor **cancelam** os do vencedor.
- O vencedor fica com a **diferença** (sucessos líquidos).

**Exemplo:** Perseguição, debate, queda de braço, Dominação vs. Força de Vontade.

**Estrutura de Dados:**

```
AçãoResistida (OpposedAction)
├── id: UUID
├── personagem_a: UUID
├── personagem_b: UUID
├── parada_a: ParadaDeDados
├── parada_b: ParadaDeDados
├── dificuldade_a: int
├── dificuldade_b: int
├── resultado_a: ResultadoDeAção
├── resultado_b: ResultadoDeAção
├── vencedor: UUID
├── sucessos_liquidos: int              # Diferença de sucessos
└── efeitos: [Efeito]
```

#### 2.5.4. Ações Reflexivas

**Definição:** Uma ação que **não consome o turno** do personagem.

**Regras:**

- O personagem pode realizar uma ação reflexiva **e** uma ação normal no mesmo turno.
- Exemplos: absorver dano, gastar Força de Vontade, ativar algumas Disciplinas.
- O Narrador decide se uma ação é reflexiva.

**Exemplo:** Absorver dano, resistir à Dominação, ativar Fortitude.

### 2.6. Sucessos Automáticos

**Decisão:** O jogador pode gastar **1 ponto de Força de Vontade** para obter **1 sucesso automático** em uma ação.

**Regras:**

- O sucesso automático é **garantido** — não pode ser cancelado por falhas críticas.
- Apenas **1 ponto de Força de Vontade** pode ser gasto por turno desta forma.
- O jogador deve declarar o gasto **antes** de rolar os dados.
- O Narrador pode vetar o uso em ações específicas.

**Exemplo:**

```
Jogador: "Vou gastar 1 ponto de Força de Vontade para ter um sucesso automático no ataque."
Narrador: "Ok, role os dados e adicione 1 sucesso."
```

**Estrutura de Dados:**

```
SucessoAutomatico (AutomaticSuccess)
├── id: UUID
├── personagem: UUID
├── forca_vontade_gasta: int            # Pontos gastos (geralmente 1)
├── sucessos_automaticos: int           # Sucessos garantidos
├── ação: UUID                          # Ação à qual se aplica
└── data: datetime
```

### 2.7. Modificadores

**Decisão:** O Narrador pode aplicar **modificadores** à dificuldade ou à parada de dados, com base nas circunstâncias.

**Tipos de Modificadores:**

| Tipo | Efeito | Exemplo |
|------|--------|---------|
| **Bônus de Dados** | +1 a +5 dados | Mirar com uma mira telescópica (+2 dados) |
| **Penalidade de Dados** | -1 a -5 dados | Ferimentos (-2 dados) |
| **Bônus de Dificuldade** | -1 a -3 na dificuldade | Condições ideais (-1 dificuldade) |
| **Penalidade de Dificuldade** | +1 a +3 na dificuldade | Condições adversas (+2 dificuldade) |
| **Sucesso Automático** | 1 sucesso garantido | Gasto de Força de Vontade |
| **Falha Automática** | 0 sucessos | Ação impossível |

**Tabela de Modificadores Comuns:**

| Circunstância | Modificador |
|---------------|-------------|
| Ferimento (Machucado) | -1 dado |
| Ferimento (Ferido) | -1 dado |
| Ferimento (Ferido Gravemente) | -2 dados |
| Ferimento (Espancado) | -2 dados |
| Ferimento (Aleijado) | -5 dados |
| Falta de Habilidade (Perícia) | +1 dificuldade |
| Falta de Habilidade (Talento) | Sem penalidade |
| Especialidade aplicável | "10" conta como 2 sucessos |
| Condições ideais | -1 dificuldade |
| Condições adversas | +1 a +3 dificuldade |
| Ações múltiplas | -1 dado por ação adicional |
| Mirar | +1 dado por turno (máx. Percepção) |
| Cobertura leve | +1 dificuldade |
| Cobertura boa | +2 dificuldade |
| Cobertura superior | +3 dificuldade |

**Estrutura de Dados:**

```
Modificador (Modifier)
├── id: UUID
├── tipo: enum                          # Dados | Dificuldade | Sucesso | Falha
├── valor: int                          # Valor do modificador
├── fonte: string                       # Ex: "Ferimento", "Mira", "Cobertura"
├── descrição: text
└── aplicável: bool                     # Se está ativo
```

### 2.8. Combate

**Decisão:** O combate é resolvido usando este motor (paradas de dados, dificuldades, ações resistidas para ataque vs. defesa), mas a especificação completa das regras de combate (iniciativa, manobras, dano, absorção e a tabela de Vitalidade) vive em um único lugar: **ADR-007, seção 2.7 (Módulo de Combate)**.

**Nota de manutenção:** esta seção existia antes com o conteúdo completo duplicado — a mesma especificação mantida em dois arquivos. Consolidado em ADR-007 porque combate é um **sistema dramático concreto** (aplicação do motor a uma situação específica de jogo), não parte do núcleo de resolução em si; este ADR-006 permanece como a única fonte do motor genérico que o combate consome.

### 2.9. Registro e Auditoria de Rolagens

**Decisão:** Todas as rolagens são **registradas em log**, para auditoria, narrativa e transparência.

**Estrutura de Dados:**

```
LogRolagem (RollLog)
├── id: UUID
├── sessao: UUID                        # Referência à sessão
├── personagem: UUID                    # Quem rolou
├── tipo: enum                          # Simples | Estendida | Resistida | Reflexiva
├── parada: ParadaDeDados               # Composição da parada
├── dificuldade: int                    # Dificuldade final
├── dados: [int]                        # Resultados individuais
├── sucessos: int
├── falhas_criticas: int
├── resultado: enum
├── descrição: text
├── visibilidade: enum                  # Público | Privado | Secreto
└── data: datetime
```

**Funcionalidades:**

- **Auditoria:** O Narrador pode revisar todas as rolagens.
- **Narrativa:** O log pode ser usado para criar uma "crônica" automática.
- **Debug:** Em caso de bugs, o log ajuda a rastrear o que aconteceu.
- **Transparência:** Os jogadores podem ver as rolagens uns dos outros (conforme configuração).
- **Rolagens Secretas:** O Narrador pode fazer rolagens secretas (visibilidade "Secreto").

### 2.10. Interface de Usuário para Rolagens

**Decisão:** Implementar uma **interface intuitiva** para rolagens, que guie o jogador e mostre os resultados.

**Componentes da UI:**

1. **Painel de Rolagem:**
   - Seleção de Atributo + Habilidade.
   - Modificadores aplicáveis (lista).
   - Campo para gasto de Força de Vontade.
   - Botão "Rolar".

2. **Resultado da Rolagem:**
   - Dados rolados (ex: [3, 8, 7, 10, 1]).
   - Dificuldade final.
   - Sucessos, falhas críticas, sucessos líquidos.
   - Resultado (Sucesso, Falha, Falha Crítica).
   - Descrição narrativa.

3. **Histórico de Rolagens:**
   - Lista das últimas rolagens.
   - Filtros por personagem, tipo, resultado.
   - Exportação para log.

4. **Painel do Narrador:**
   - Todas as rolagens em tempo real.
   - Possibilidade de ignorar ou modificar resultados.
   - Rolagens secretas.

### 2.11. Geração de Números Aleatórios (RNG)

**Decisão:** A aleatoriedade é gerada no **backend**, usando um **RNG criptograficamente seguro**.

**Justificativa:**

- **Justiça:** Garante que todos os jogadores tenham a mesma chance.
- **Anti-Trapaça:** Evita que jogadores manipulem os resultados no cliente.
- **Auditoria:** Permite que o Narrador verifique se uma rolagem foi justa.

**Implementação:**

- **Backend:** Usar `crypto.randomInt()` (Node.js) ou `secrets.randbelow()` (Python) para gerar números aleatórios.
- **Cliente:** Apenas exibe os resultados; não gera números.
- **Seed:** Opcionalmente, usar uma seed pública para permitir verificação.

**Exemplo (Node.js):**

```javascript
const crypto = require('crypto');

function rollDice(count, sides) {
  const results = [];
  for (let i = 0; i < count; i++) {
    results.push(crypto.randomInt(1, sides + 1));
  }
  return results;
}

// Exemplo: rolar 8 dados de 10 lados
const dados = rollDice(8, 10);
console.log(dados); // [3, 8, 7, 10, 1, 5, 9, 6]
```

### 2.12. Flexibilidade e Override do Narrador

**Decisão:** O Narrador tem **autoridade final** sobre todas as rolagens e pode **sobrescrever** qualquer resultado.

**Funcionalidades:**

- **Modificar Dificuldade:** O Narrador pode ajustar a dificuldade antes ou depois da rolagem.
- **Ignorar Resultado:** O Narrador pode declarar uma rolagem "nula" e pedir uma nova.
- **Sucesso/Falha Automática:** O Narrador pode declarar sucesso ou falha sem rolar.
- **Rolagem Secreta:** O Narrador pode rolar dados sem que os jogadores vejam.
- **Override de Resultado:** O Narrador pode mudar o resultado (ex: transformar uma falha em sucesso).
- **Justificativa:** O Narrador pode adicionar uma justificativa narrativa para o override.

**Estrutura de Dados:**

```
OverrideNarrador (NarratorOverride)
├── id: UUID
├── rolagem: UUID                       # Referência à rolagem original
├── narrador: UUID                      # Quem fez o override
├── tipo: enum                          # Modificar | Ignorar | Forçar | Secreto
├── valor: string                       # Novo valor (se aplicável)
├── justificativa: text                 # Por que o override foi feito
└── data: datetime
```

## 3. Consequências

### 3.1. Positivas

- **Fidelidade ao Sistema Storyteller:** O motor implementa todas as regras do Capítulo Cinco.
- **Justiça e Anti-Trapaça:** O RNG no backend garante que todos os jogadores tenham as mesmas chances.
- **Transparência:** Os jogadores veem os resultados e entendem o que aconteceu.
- **Auditoria:** Todas as rolagens são registradas em log, permitindo revisão.
- **Flexibilidade:** O Narrador tem autoridade final e pode sobrescrever qualquer resultado.
- **Automação:** Cálculos de parada de dados, dificuldade, sucessos e falhas são automáticos.
- **Base para ADRs Futuros:** O Motor de Resolução estabelece as fundações para os Sistemas Dramáticos (ADR-007) e a Moralidade (ADR-008).

### 3.2. Negativas

- **Complexidade de Implementação:** Implementar todas as regras de ações (simples, estendidas, resistidas, reflexivas) é um esforço significativo.
- **Performance:** Rolagens em tempo real podem impactar a performance. Otimizações serão necessárias.
- **Curva de Aprendizado:** Novos jogadores podem se sentir sobrecarregados com tantas opções. A UI deve guiar o processo.
- **Dependência de Backend:** O RNG no backend significa que o jogo não funciona offline para rolagens.
- **Latência:** O round-trip para o backend pode adicionar latência perceptível. Estratégias de cache e otimização serão necessárias.
- **Manutenção:** À medida que novas regras são lançadas, o motor precisa ser atualizado.

### 3.3. Alternativas Descartadas

| Alternativa | Motivo da Rejeição |
|-------------|-------------------|
| **RNG no Cliente** | Permitiria trapaças; menos justo. |
| **Rolagem Manual (dados físicos)** | Perde a automação e a auditoria. |
| **Sistema de Rolagem Simplificado** | Perderia a fidelidade ao Storyteller. |
| **Sem Override do Narrador** | Limitaria a flexibilidade e a autoridade do Narrador. |
| **Sem Log de Rolagens** | Impossibilitaria auditoria e narrativa automática. |

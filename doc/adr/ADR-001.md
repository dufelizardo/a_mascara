# ADR-001: Definição da Plataforma e Arquitetura Geral

## 1. Contexto

O objetivo do projeto é desenvolver uma **plataforma digital colaborativa** que permita a grupos de jogadores vivenciarem a experiência de RPG de mesa de **Vampiro: A Máscara (Edição de 20º Aniversário)** de forma remota, preservando a essência narrativa e interpretativa do jogo original.

Diferente de um videogame RPG tradicional — onde a narrativa, as regras e as consequências são pré-programadas — esta plataforma deve atuar como uma **mesa virtual (VTT — Virtual Tabletop)**, oferecendo ferramentas que **auxiliem Narradores e Jogadores** sem substituir a liberdade criativa e a mediação humana que definem o RPG de mesa.

O sistema precisa suportar:

- Criação e gerenciamento de fichas de personagem complexas (Atributos, Habilidades, Disciplinas, Virtudes, Antecedentes, Humanidade/Trilhas, etc.).
- Rolagem de dados (paradas de D10) com aplicação de dificuldades e sucessos.
- Comunicação em tempo real entre os participantes (texto, voz e compartilhamento de resultados).
- Ferramentas para o Narrador (gerenciamento de cenas, NPCs, rolagem secreta, controle de crônica).
- Persistência de dados de campanhas, personagens e histórico de sessões.
- Aplicação automatizada das regras do sistema (frenesi, Rötschreck, Laço de Sangue, degeneração de Humanidade, etc.), mas com espaço para **override manual** pelo Narrador.

A escolha da arquitetura é fundamental para garantir **escalabilidade, manutenibilidade, baixa latência em interações em tempo real e boa experiência de usuário**.

---

## 2. Decisão

Decidimos construir a plataforma como uma **Aplicação Web (Web Application)**, seguindo uma arquitetura **Cliente-Servidor desacoplada**, com os seguintes componentes:

### 2.1. Tipo de Aplicação

**Aplicação Web Progressiva (PWA)** acessível via navegador moderno (Chrome, Firefox, Safari, Edge), sem necessidade de instalação nativa. A PWA permitirá:

- Instalação opcional no dispositivo do usuário (desktop/mobile).
- Funcionamento parcial offline para consulta de fichas e regras.
- Atualizações centralizadas (sem necessidade de distribuição por lojas de aplicativos).

### 2.2. Arquitetura Geral

**Cliente-Servidor com API dedicada e comunicação em tempo real.**

```
┌─────────────────────────────────────────────────────────────┐
│                     CLIENTE (Navegador / PWA)               │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  Frontend SPA (React / Vue / Svelte)                  │  │
│  │  - Ficha de Personagem Interativa                     │  │
│  │  - Mesa de Jogo (chat, tabuleiro, rolagem)            │  │
│  │  - Painel do Narrador                                 │  │
│  └───────────────────────────────────────────────────────┘  │
└───────────────┬─────────────────────────────┬───────────────┘
                │ HTTPS (REST/GraphQL)        │ WSS (WebSockets)
                ▼                             ▼
┌─────────────────────────────────────────────────────────────┐
│                    BACKEND (API + Realtime)                 │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │  API REST /  │  │  Servidor    │  │  Motor de Regras │   │
│  │  GraphQL     │  │  WebSocket   │  │  (Game Rules     │   │
│  │              │  │  (Socket.IO) │  │   Engine)        │   │
│  └──────────────┘  └──────────────┘  └──────────────────┘   │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  Camada de Autenticação (JWT / OAuth)                  │ │
│  └────────────────────────────────────────────────────────┘ │
└───────────────┬─────────────────────────────┬───────────────┘
                │                             │
                ▼                             ▼
┌───────────────────────────┐   ┌───────────────────────────┐
│  BANCO DE DADOS PRINCIPAL │   │  CACHE / SESSÕES          │
│  (PostgreSQL)             │   │  (Redis)                  │
└───────────────────────────┘   └───────────────────────────┘
```

### 2.3. Stack Tecnológica Proposta

| Camada                  | Tecnologia Sugerida                          | Justificativa                                                                 |
|-------------------------|----------------------------------------------|-------------------------------------------------------------------------------|
| **Frontend**            | React (com Next.js) ou Vue.js (com Nuxt.js)  | Ecossistema maduro, componentização, SSR/SSG, grande comunidade.              |
| **Estilização**         | Tailwind CSS + shadcn/ui                     | Rapidez no desenvolvimento, consistência visual, tema "dark" nativo.          |
| **Comunicação HTTP**    | Axios (REST) ou Apollo Client (GraphQL)      | Padrões consolidados, bom suporte a interceptadores e cache.                  |
| **Comunicação Realtime**| Socket.IO ou WebSocket nativo                | Sincronização de fichas, chat, rolagem compartilhada e tabuleiro em tempo real.|
| **Backend**             | Node.js (NestJS) ou Python (FastAPI)         | Alta performance, tipagem forte, facilidade para implementar o Motor de Regras.|
| **Motor de Regras**     | Módulo dedicado no backend                   | Centraliza a lógica do sistema Storyteller (d10, dificuldades, Disciplinas).  |
| **Banco de Dados**      | PostgreSQL                                   | Relacional, robusto, ideal para dados estruturados (fichas, campanhas, logs). |
| **Cache / Realtime**    | Redis                                        | Sessões, Pub/Sub para WebSockets, cache de consultas frequentes.              |
| **Autenticação**        | JWT + OAuth (Google, Discord)                | Simples, seguro, integração com comunidades de RPG (Discord é essencial).     |
| **Hospedagem**          | Vercel (frontend) + Railway/Render/AWS (backend) | Deploy rápido, escalabilidade sob demanda, custo inicial baixo.           |
| **Armazenamento**       | S3-compatible (Cloudflare R2, AWS S3)        | Imagens de fichas, mapas, assets de campanha.                                 |

### 2.4. Princípios Arquiteturais

1. **Separação de Responsabilidades:** Frontend cuida da apresentação e interação; Backend cuida da lógica, persistência e regras.
2. **Motor de Regras Centralizado:** Toda a lógica do sistema Storyteller (paradas de dados, dificuldades, Disciplinas, Humanidade, Frenesi) reside no backend, garantindo consistência entre todos os clientes.
3. **Override do Narrador:** O Narrador tem autoridade final. Qualquer resultado automatizado pode ser sobrescrito manualmente.
4. **Tempo Real como Cidadão de Primeira Classe:** Sincronização instantânea de fichas, dados e tabuleiro é um requisito, não um extra.
5. **Modularidade:** O sistema deve ser extensível para futuras implementações (outros jogos do Mundo das Trevas, novos Clãs, linhagens, etc.).
6. **Privacidade e Segurança:** Dados de campanha são privados ao grupo. Autenticação e autorização rigorosas.

## 3. Consequências

### 3.1. Positivas

- **Acessibilidade universal:** Qualquer pessoa com um navegador pode jogar, sem barreiras de sistema operacional.
- **Atualizações centralizadas:** Novas funcionalidades e correções são entregues instantaneamente a todos os usuários.
- **Consistência de regras:** O Motor de Regras no backend garante que todos os grupos joguem com as mesmas regras aplicadas da mesma forma.
- **Escalabilidade:** A arquitetura desacoplada permite escalar horizontalmente backend e banco de dados conforme a demanda.
- **Integração com a comunidade:** Autenticação via Discord facilita a adoção por grupos que já usam a plataforma para se organizar.
- **Custo inicial baixo:** Utilização de serviços cloud com camadas gratuitas ou de baixo custo permite validar o MVP rapidamente.

### 3.2. Negativas

- **Dependência de conexão com a internet:** A experiência completa exige conexão. O modo offline será limitado à consulta de fichas e regras.
- **Complexidade do tempo real:** WebSockets e sincronização de estado exigem cuidado adicional com concorrência, reconexão e integridade de dados.
- **Curva de aprendizado da stack:** A equipe precisa dominar frontend, backend, WebSockets e banco de dados relacionais.
- **Latência em rolagens:** Se mal implementado, o round-trip para o backend pode adicionar latência perceptível. Estratégias de cache e otimização serão necessárias.
- **Dependência de terceiros:** Serviços de hospedagem, autenticação e armazenamento introduzem pontos de falha externos.

### 3.3. Alternativas Descartadas

| Alternativa                        | Motivo da Rejeição                                                                                     |
|------------------------------------|--------------------------------------------------------------------------------------------------------|
| **Aplicativo Desktop (Electron)**  | Distribuição mais complexa, atualizações manuais, maior consumo de recursos, menor alcance inicial.    |
| **Aplicativo Mobile Nativo**       | Custo elevado (iOS + Android separados), ciclo de aprovação em lojas, overkill para um MVP.           |
| **Videogame RPG single-player**    | Perde a essência colaborativa e narrativa do RPG de mesa; escopo massivo e inviável para o objetivo.  |
| **Plataforma baseada em planilhas**| Solução frágil, não escalável, sem tempo real, experiência de usuário pobre.                          |

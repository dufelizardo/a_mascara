# ADR-018: DevOps, CI/CD e Infraestrutura de Deploy

- **Status:** Proposto
- **Data:** 2026-09-14
- **Decisores:** [Seu Nome / Equipe]
- **Contexto Técnico:** Definição dos ambientes, pipeline de entrega contínua, observabilidade e estratégia de backup
- **Tags:** `devops`, `ci-cd`, `infraestrutura`, `observabilidade`, `backup`, `transversal`
- **Depende de:** ADR-001 (Plataforma), ADR-014 (Escopo do MVP), ADR-016 (Privacidade — retenção de backups), ADR-017 (Testes)
- **Tipo:** ADR Transversal

---

## 1. Contexto

O ADR-001 sugere "Vercel (frontend) + Railway/Render/AWS (backend)" como hospedagem, mas não define ambientes, pipeline de CI/CD, estratégia de observabilidade, backup do banco de dados ou processo de rollback. Sem isso, cada deploy é manual e arriscado, e um incidente em produção (perda de dados, bug crítico no Motor de Resolução) não tem um plano de resposta definido.

Este ADR fecha essa lacuna, mantendo a escolha de hospedagem gerenciada do ADR-001 (evitando complexidade operacional desnecessária para o estágio de MVP) e definindo o que falta ao redor dela.

---

## 2. Decisão

### 2.1. Ambientes

| Ambiente | Propósito | Deploy |
|----------|-----------|--------|
| **Desenvolvimento local** | Cada desenvolvedor roda a stack via Docker Compose (Postgres + Redis + backend + frontend) | Manual |
| **Preview (por PR)** | Ambiente efêmero por Pull Request, para revisão visual e QA exploratório | Automático na abertura do PR |
| **Staging** | Espelha produção; onde os testes E2E (ADR-017) rodam antes da promoção | Automático a cada merge na branch principal |
| **Produção** | Ambiente real de usuários | Manual (promoção de staging após E2E verde) no MVP; automático é revisitado pós-MVP |

### 2.2. Pipeline de CI/CD

**Decisão:** Pipeline único (GitHub Actions ou equivalente) com estágios sequenciais, reaproveitando os gates definidos no ADR-017.

```
PR aberto
  → Lint + Type-check
  → Testes unitários + integração (ADR-017 §2.5)
  → Build (frontend e backend)
  → Deploy de Preview
  → (revisão humana + aprovação)
Merge na branch principal
  → Reexecuta suíte completa
  → Deploy automático em Staging
  → Testes E2E (ADR-017) contra Staging
  → (E2E verde) → Notificação de "pronto para promover"
Promoção manual a Produção
  → Migração de banco de dados (ver 2.5)
  → Deploy do backend (rolling, sem downtime)
  → Deploy do frontend
  → Smoke test automático pós-deploy
```

### 2.3. Gestão de Segredos

**Decisão:** Segredos (client secret OAuth, chave de assinatura JWT, credenciais de banco, chave de API de IA quando ativada) vivem **apenas** no cofre de variáveis de ambiente do provedor de hospedagem (Vercel/Railway) e no cofre de secrets do CI — nunca em arquivo versionado, nem em `.env` commitado.

- Rotação de chave de assinatura JWT documentada como procedimento manual (invalidando sessões ativas) para casos de comprometimento.
- Acesso ao cofre de produção restrito à mesma lista de pessoas com papel `Moderador`/mantenedor (ligado ao ADR-015).

### 2.4. Observabilidade

| Componente | Ferramenta (proposta) | Propósito |
|------------|--------------------------|------------|
| **Logs estruturados** | JSON logs centralizados no provedor de hospedagem | Depuração e auditoria (ligado ao log de ADR-015/016) |
| **Rastreamento de erros** | Sentry (ou equivalente) | Captura de exceções não tratadas no frontend e backend |
| **Métricas** | Dashboard básico: latência de API, taxa de erro, conexões WebSocket ativas | Detecção de degradação de performance |
| **Alertas** | Alerta automático se taxa de erro > limiar ou serviço fora do ar | Resposta rápida a incidentes |
| **Uptime** | Verificação externa (ping) do endpoint de saúde (`/health`) | Detecção de indisponibilidade independente da aplicação |

### 2.5. Banco de Dados: Migrações e Backup

**Decisão:**
- **Migrações:** gerenciadas por ferramenta de migração do ORM escolhido (ex.: Prisma Migrate), versionadas no repositório, revisadas em PR como qualquer mudança de código; aplicadas automaticamente no início do deploy em Staging/Produção, nunca manualmente contra o banco.
- **Backup:** backup automático diário do Postgres com retenção de 30 dias, mais backup incremental/WAL para permitir *point-in-time recovery* de até 7 dias — alinhado à política de retenção do ADR-016.
- **Teste de restauração:** processo de restauração de backup testado manualmente a cada trimestre (um backup não testado não é um backup confiável).

### 2.6. Rollback

**Decisão:** Deploy do backend e frontend deve ser revertível para a versão anterior em um comando/clique, sem depender de reverter a migração de banco (migrações devem ser, sempre que possível, **aditivas e compatíveis com a versão anterior do código** por pelo menos um deploy — expand/contract pattern), para permitir rollback de aplicação sem rollback de schema.

### 2.7. Escalabilidade (Nível MVP)

**Decisão:** Para o MVP (ADR-014), a infraestrutura roda em instâncias gerenciadas de escala única (sem auto-scaling horizontal), com Redis usado tanto para cache quanto para Pub/Sub de WebSocket entre instâncias — preparando o terreno para escala horizontal futura sem exigi-la agora. Escala horizontal real do WebSocket (múltiplas instâncias de backend) é revisitada quando o número de crônicas simultâneas justificar.

## 3. Consequências

### 3.1. Positivas
- Pipeline automatizado com gates de teste (ADR-017) reduz risco de regressão chegando a produção.
- Ambiente de preview por PR acelera revisão visual sem precisar rodar a stack localmente.
- Estratégia de migração aditiva + rollback de aplicação sem rollback de schema reduz o risco de incidentes de deploy.
- Backup com teste de restauração trimestral evita a armadilha comum de "backup que nunca foi restaurado com sucesso".

### 3.2. Negativas
- Promoção manual a produção no MVP adiciona uma etapa humana ao ciclo de release — aceito como troca deliberada por segurança nesta fase inicial.
- Observabilidade (Sentry, dashboards, alertas) tem custo recorrente e requer configuração cuidadosa para não vazar dados pessoais nos logs de erro (ligado ao ADR-016).
- Manter migrações sempre aditivas por um deploy extra é uma disciplina de engenharia que precisa ser reforçada em revisão de código.

### 3.3. Alternativas Descartadas

| Alternativa | Motivo da Rejeição |
|-------------|---------------------|
| **Deploy automático direto para produção a cada merge** | Risco alto demais sem um histórico de estabilidade; revisitar pós-MVP com feature flags. |
| **Infraestrutura própria (Kubernetes autogerenciado)** | Complexidade operacional desnecessária para o estágio de MVP; hospedagem gerenciada (ADR-001) é suficiente. |
| **Sem ambiente de Staging (testar direto em produção)** | Inaceitável dado que o Motor de Resolução exige alta confiabilidade (ADR-017); staging é onde o E2E roda antes de expor usuários reais. |
| **Rollback via restauração de backup de banco** | Rollback de aplicação deve ser rápido (segundos/minutos); depender de restauração de backup para reverter um bug de código é lento demais e arriscado. |

## Atualização — scaffolding de branches e pipeline implementado

O fluxo de branches (2.1, adaptado: `developer` → `qaa` → `homologacao` → `main`, o mesmo modelo
já validado em produção no projeto mais_saude_publica) e a pipeline de gate (`.github/workflows/pipeline.yml`,
estágios `test` → `analyze` → `acceptance`) foram criados. Como ainda não existe código de
aplicação (só os ADRs em `doc/`), cada estágio detecta a ausência de `package.json`/`Dockerfile` e
vira no-op automaticamente — não é necessário editar o workflow quando o código real for
adicionado, desde que a raiz do projeto exponha os scripts `lint`/`typecheck`/`test` e um
`Dockerfile`. `.github/workflows/auto-merge.yml` também foi criado, espelhando a mesma lógica do
mais_saude_publica (merge administrativo após os checks obrigatórios passarem).

**Pendente (ação manual fora deste repositório, requer conta do usuário):**
- Criar o repositório remoto no GitHub e dar push das branches `main`/`developer`/`qaa`/`homologacao`.
- Configurar branch protection (`test`, `analyze` como checks obrigatórios) e o Ruleset de
  aprovação para terceiros nas 4 branches, como feito no mais_saude_publica (ADR-0011 daquele
  projeto).
- Criar o secret `AUTOMERGE_PAT` (Personal Access Token fine-grained, com `Contents`, `Pull
  requests` e `Administration: Read and write`) para o `auto-merge.yml` funcionar.
- Os estágios de build de imagem Docker, deploy e infraestrutura (K3s/ArgoCD ou equivalente) ficam
  para quando houver de fato uma aplicação para empacotar — ver ADR-014 (Escopo do MVP).

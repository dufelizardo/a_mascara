# ADR-015: Autenticação, Autorização e Modelo de Convite/Grupos

- **Status:** Proposto
- **Data:** 2026-09-14
- **Decisores:** [Seu Nome / Equipe]
- **Contexto Técnico:** Definição do mecanismo de autenticação, do modelo de autorização por papel e do fluxo de convite para crônicas
- **Tags:** `autenticação`, `autorização`, `oauth`, `jwt`, `convites`, `grupos`, `segurança`, `transversal`
- **Depende de:** ADR-001 (Plataforma), ADR-002 (Máscara como mecânica de informação), ADR-004 (Ficha de Personagem), ADR-014 (Escopo do MVP)
- **Tipo:** ADR Transversal — **bloqueante para o MVP** (ADR-014, seção 2.4)

## 1. Contexto

O ADR-001 menciona "JWT + OAuth (Google, Discord)" como escolha de autenticação, mas nunca detalha o mecanismo, o modelo de sessão, o modelo de papéis dentro de uma crônica, nem o fluxo de convite de jogadores. Como a plataforma lida com **contas de usuários reais** desde o primeiro login — não apenas dados fictícios de personagem — este ADR é pré-requisito para qualquer código de produção, conforme já sinalizado no ADR-014.

Este ADR precisa responder:
- Como um usuário se autentica (login/senha? só OAuth? ambos?).
- Como uma sessão é mantida e revogada.
- Quem pode fazer o quê dentro de uma crônica (Narrador vs Jogador vs Observador).
- Como um Narrador convida jogadores, e como o convite se transforma em associação a uma crônica.
- Como isso se conecta ao controle de visibilidade de informação já definido no ADR-002 (Público/Privado/Secreto).

---

## 2. Decisão

### 2.1. Mecanismo de Autenticação

**Decisão:** OAuth como método primário (Discord e Google), com login por e-mail/senha como alternativa, ambos emitindo o mesmo par de tokens internos.

| Método | Prioridade | Justificativa |
|--------|-----------|----------------|
| **Discord OAuth** | Primário | A maioria dos grupos de RPG já usa Discord para se organizar; reduz fricção de cadastro. |
| **Google OAuth** | Secundário | Cobertura para quem não usa Discord. |
| **E-mail + senha** | Alternativa | Necessário para usuários sem conta OAuth; senha com hash Argon2id, nunca texto plano. |

**Escopos OAuth solicitados:** apenas identificação básica (id, nome de exibição, avatar, e-mail se disponível) — nunca lista de servidores, mensagens ou permissões administrativas do Discord.

### 2.2. Sessão e Tokens

**Decisão:** Autenticação baseada em **JWT de curta duração (access token) + refresh token opaco de longa duração**, seguindo o padrão de rotação de refresh token.

```
AccessToken (JWT)
├── sub: UUID              # id do usuário
├── exp: timestamp         # expira em 15 minutos
├── papel_plataforma: enum # Usuário | Moderador (não há "admin de crônica" aqui — ver 2.3)
└── iat: timestamp

RefreshToken (opaco, armazenado hasheado no banco)
├── id: UUID
├── usuario: UUID
├── expira_em: datetime    # 30 dias
├── revogado: bool
├── dispositivo: string    # user agent, para o usuário revogar sessões individualmente
└── criado_em: datetime
```

**Regras:**
- O access token é enviado como `Authorization: Bearer` em requisições HTTP e usado para autenticar o handshake do WebSocket.
- O refresh token é armazenado em **cookie httpOnly + Secure + SameSite=Strict** (nunca em `localStorage`, para reduzir exposição a XSS).
- Rotação: a cada uso do refresh token, um novo é emitido e o anterior é invalidado (detecção de reuso indica possível roubo de token → revoga toda a família de tokens).
- O usuário pode ver e revogar sessões ativas individualmente (tela "Dispositivos Conectados").

### 2.3. Modelo de Autorização por Papel

**Decisão:** Autorização é **contextual à crônica** — não existe um papel global de "administrador de crônica" na plataforma, apenas papéis dentro de cada crônica específica.

```
MembroCrônica (ChronicleMember)
├── id: UUID
├── crônica: UUID
├── usuário: UUID
├── papel: enum                # Narrador | Jogador | Observador
├── personagem: UUID           # Referência ao personagem (se Jogador)
├── entrou_em: datetime
└── status: enum                # Ativo | Removido | Convite Pendente
```

**Matriz de Permissões (MVP):**

| Ação | Narrador | Jogador (próprio personagem) | Jogador (outros) | Observador |
|------|----------|-------------------------------|-------------------|-------------|
| Ver ficha (campos Públicos) | ✅ | ✅ | ✅ | ✅ |
| Ver ficha (campos Privados) | ✅ | ✅ (próprio) | ❌ | ❌ |
| Ver ficha (campos Secretos) | ✅ | ❌ | ❌ | ❌ |
| Editar ficha | ✅ | ✅ (próprio, campos permitidos) | ❌ | ❌ |
| Rolar dados | ✅ | ✅ | ❌ | ❌ |
| Fazer rolagem secreta | ✅ | ❌ | ❌ | ❌ |
| Criar/gerenciar NPC | ✅ | ❌ | ❌ | ❌ |
| Convidar/remover membro | ✅ | ❌ | ❌ | ❌ |
| Editar regras da casa | ✅ | ❌ | ❌ | ❌ |

Esta matriz referencia diretamente os níveis de visibilidade **Público/Privado/Secreto** já definidos no ADR-002 (seção 2.6) — este ADR define **quem** tem cada papel; o ADR-002 já define **o que** cada nível de visibilidade expõe.

**Papel de plataforma (fora do escopo de uma crônica):** apenas `Usuário` (padrão) e `Moderador` (equipe da plataforma, para moderação de denúncias — ver ADR-016). Não há hierarquia de "admin de crônica" acima do Narrador: o Narrador é sempre a autoridade máxima dentro da própria crônica, consistente com o princípio já estabelecido no ADR-009.

### 2.4. Fluxo de Convite

**Decisão:** Convite por **link com token de uso único ou limitado**, sem exigir que o convidado já tenha conta antes do convite ser gerado.

```
Convite (Invite)
├── id: UUID
├── crônica: UUID
├── criado_por: UUID            # Narrador
├── token: string                # aleatório, criptograficamente seguro
├── papel_padrão: enum           # Jogador | Observador
├── usos_máximos: int            # 1 (padrão) ou N para convite de grupo
├── usos_atuais: int
├── expira_em: datetime          # 7 dias por padrão
└── status: enum                 # Ativo | Expirado | Revogado
```

**Fluxo:**
1. Narrador gera um link de convite (opcionalmente para um papel específico).
2. O link é compartilhado fora da plataforma (Discord, e-mail, etc.) — a plataforma não envia convites automaticamente no MVP.
3. Quem acessa o link, se não tiver conta, passa pelo fluxo de autenticação (2.1) e depois é automaticamente associado à crônica como `MembroCrônica`.
4. O Narrador pode revogar um convite ativo ou remover um membro a qualquer momento.

### 2.5. Segurança

| Medida | Descrição |
|--------|-----------|
| **Rate limiting** | Login e refresh limitados por IP e por conta (ex.: 5 tentativas/min) para mitigar força bruta. |
| **Hash de senha** | Argon2id com salt único por usuário. |
| **Revogação em cascata** | Ao trocar a senha ou detectar reuso de refresh token, todas as sessões ativas são revogadas. |
| **CSRF** | Cookies com `SameSite=Strict`; mutações via API exigem também o access token no header (defesa em profundidade). |
| **Auditoria** | Login, logout, revogação de sessão e mudanças de papel de membro são registrados em log (retenção conforme ADR-016). |
| **Verificação de e-mail** | Obrigatória para contas criadas por e-mail/senha, antes de poder criar ou entrar em crônicas. |

## 3. Consequências

### 3.1. Positivas
- Fluxo de login de baixa fricção via Discord/Google, alinhado ao público-alvo de RPG.
- Modelo de papel **por crônica** (não global) é simples de raciocinar e evita necessidade de um sistema de permissões genérico complexo no MVP.
- Rotação de refresh token com detecção de reuso é um padrão de segurança comprovado, sem exigir infraestrutura adicional.
- O convite por link sem pré-cadastro reduz fricção para novos jogadores.

### 3.2. Negativas
- Múltiplos provedores OAuth + e-mail/senha aumentam a superfície de testes de autenticação.
- Sem papel de "admin de crônica" acima do Narrador, uma crônica sem Narrador ativo (ex.: conta excluída) fica órfã — precisa de um processo manual de transferência de titularidade (não coberto neste ADR; considerar em iteração futura).
- Rate limiting e auditoria adicionam complexidade operacional que precisa de infraestrutura de observabilidade (ver ADR-018).

### 3.3. Alternativas Descartadas

| Alternativa | Motivo da Rejeição |
|-------------|---------------------|
| **Apenas OAuth (sem e-mail/senha)** | Excluiria usuários sem conta Discord/Google; barreira de entrada desnecessária. |
| **Sessão baseada em cookie de sessão opaco (sem JWT)** | Dificultaria autenticação do WebSocket sem uma chamada extra ao banco a cada handshake. |
| **Papel global de "admin de crônica"** | Adicionaria uma camada de hierarquia sem necessidade real no MVP; o Narrador já é a autoridade máxima. |
| **Convite exigindo conta pré-existente** | Aumentaria a fricção de entrada de novos jogadores, contrariando o objetivo de baixa fricção do produto. |
